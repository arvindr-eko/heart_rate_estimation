--- cons_wait_s: DONE ---
13-point grid (1.0 to 8.0), all other params at BASE_DSP (pctl=0.35). Full results saved in
DEDICATED_SWEEP_CONS_WAIT_S_2026-07-27.txt and dedicated_sweep_cons_wait_s_progress.pkl.

MAJOR FINDING -- a CLIFF, not a smooth curve:
  cons_wait_s   correct%   half   no_display%
  1.0-3.5       ~52%       126-134   ~40%      (flat plateau, "short-wait" regime)
  4.0 (shipped) 67.0%      333       22.8%     (best of all 13 points, right at the cliff edge)
  4.5-8.0       65.6%->50.6% (declining)        233->255 (noisy)   25.4%->42.3% (rising)
The jump between 3.5 and 4.0 is the single biggest change in the whole grid -- shipped's default sits
right at the good edge of a cliff, not comfortably inside a stable plateau.

MECHANISM (Daniel's hypothesis, confirmed correct via code inspection): single_win_min defaults to
4.0s, and win_r (the autocorrelation result) requires len(seg_clean_ar) >= win_nsamp, where win_nsamp
is based on win_sec, which equals EXACTLY single_win_min whenever the estimator is still in its "wait"
period (since_event < frozen_wait_s, which starts at cons_wait_s). So whenever cons_wait_s <
single_win_min, the algorithm starts ATTEMPTING to display before enough real audio has accumulated to
fill the minimum window -- correctly returning no_display for a stretch, not "garbage," but insufficient
data. Since onset/spike events reset this wait repeatedly through a recording (not just once at file
start), the effect is a persistent plateau, not a one-time startup blip.
NUANCE: the short-wait regime is not lower-quality per attempt -- half-rate AS A FRACTION OF DISPLAYED
TICKS is actually lower below 4.0 (~0.8%) than at/above it (~1.6%). It's a coverage/quality-per-attempt
tradeoff: short wait shows less but is pickier; once cons_wait_s clears single_win_min, it shows almost
everything, including tougher windows a shorter wait would have skipped as no_display.

NOT YET DONE (tomorrow's plan): a confirmatory test proposed but not yet run -- if the mechanism is
really the cons_wait_s vs single_win_min ALIGNMENT (not cons_wait_s in isolation), then the cliff's
LOCATION should move if single_win_min changes. E.g. single_win_min=2.0 with cons_wait_s=3.0 should
land in the GOOD regime; single_win_min=6.0 with the same cons_wait_s=3.0 should reproduce the BAD
regime. This should be run as part of (or just before) the single_win joint sweep tomorrow -- it's the
single most informative next test, since it would either confirm or falsify the mechanism directly
rather than just fitting a plausible story to one parameter's marginal sweep.
